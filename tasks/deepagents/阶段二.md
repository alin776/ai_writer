## 一、任务 2.1 — 创建 DeepAgents 写作 Agent

### 核心理解

重构后的 Agent 创建从"多组件拼装"变为"一个函数调用"：

```
现在（WritingAgentGraph 单例，多组件）:
  ├── HTTPAIService          ← 自己封装的 AI 调用层
  ├── ContextManager         ← 自己写的上下文管理
  ├── PromptManager          ← Jinja2 模板引擎
  │   ├── system_agent_prompt.yaml
  │   ├── creative_writing_prompt.yaml
  │   └── writing_agent.yaml
  ├── IntentClassifier       ← 意图分类器
  ├── ToolExecutor           ← 工具执行器
  ├── EventParser            ← 事件解析器
  └── ResponseBuilder        ← 响应构建器

重构后（一个函数调用）:
  agent = create_deep_agent(
      model=...,
      system_prompt=...,        ← 动态拼接
      backend=BufferedFilesystemBackend(...),
      tools=[semantic_search],
      checkpointer=MemorySaver(),
  )
```

上面那些 ContextManager、PromptManager、IntentClassifier、EventParser、ResponseBuilder —— 全部由 DeepAgents 框架内置替代。

### system_prompt 拼接方式（纠正）

阶段一文档写的是"追加在 base_prompt 之后"，实际顺序是：

```
┌─────────────────────────────┐
│ 自定义 system_prompt（在前） │  ← 我们写的领域指导
├─────────────────────────────┤
│ BASE_AGENT_PROMPT（在后）    │  ← 框架内置的工具使用指南
└─────────────────────────────┘
```

来源：DeepWiki 官方文档 — "The custom prompt is placed first, followed by two newlines and BASE_AGENT_PROMPT"

### system_prompt 设计原则

**不写什么（框架已经教了）：**
- 怎么用 read_file / write_file / edit_file / ls / glob / grep
- 怎么做 Planning（write_todos / read_todos）
- 怎么管理上下文（自动摘要、大输出存文件）
- 写作技巧、爽点公式、好坏示例（LLM 自己会写小说，不需要每次消耗 token 重复教）

**只写什么（领域专属指导）：**
1. 你是谁（角色定位）
2. 你在写什么书（动态元数据）
3. 文件放哪里（文件规范约定）
4. 行为规则（系统级约束）

### system_prompt 完整模板

```python
def build_system_prompt(work: Work) -> str:
    """从 works 表元数据构建 system_prompt"""
    return f"""你是一位网络小说作家。

## 当前作品
- 书名：《{work.title}》
- 类型：{work.genre.value}
- 简介：{work.description or '暂无'}

## 文件规范
- outline.md      大纲（章节划分、剧情走向）
- characters.md   人物设定（外貌、性格、关系）
- worldview.md    世界观（社会规则、力量体系）
- chapters/XX.md  章节正文（XX 为两位数序号）
- notes/          自由笔记区

章节文件开头必须包含 frontmatter：
---
title: 章节标题
status: draft
---

## 行为规则
1. 动笔前先读：创作/续写/改写前，先读取相关文件（大纲、人物、前文）
2. 保持一致：人物性格、世界观设定、时间线不能自相矛盾
3. 已有文件用 edit_file 修改，新文件用 write_file 创建
4. 一次续写不超过 3000 字，宁短勿烂
"""
```

约 25 行，纯领域指导，零工具说明。

### 为什么不在 system_prompt 里写"写作技巧"

| 放 system_prompt | 不放（靠 LLM 自身能力） |
|---|---|
| 每次请求都消耗 token | 零额外消耗 |
| 写死了风格，缺乏灵活性 | 用户可以通过对话动态调整风格 |
| system_prompt 越长，LLM 注意力越分散 | 短 prompt 聚焦在真正重要的约束上 |

如果后续需要风格指导，可以放 `notes/writing_guide.md`，Agent 需要时自己 `read_file` 去查。

### works 表 → system_prompt 的数据流

```
用户打开作品
    │
    ▼
API 层：从 works 表查询 work 对象
    │
    ▼
build_system_prompt(work)  →  拼接 system_prompt
    │
    ▼
create_deep_agent(system_prompt=..., backend=..., ...)
    │
    ▼
agent.invoke({"messages": [...]}, config={"configurable": {"thread_id": ...}})
```

works 表保留，角色从"章节存储的父表"变为"给 Agent prompt 提供元数据的来源"。

## 二、任务 2.1.2 — BufferedFilesystemBackend

### 是什么

一个带缓冲区的文件系统后端。Agent 的写操作（write_file / edit_file）不直接落盘，而是存在内存缓冲区里。Agent 跑完后，所有改动汇总展示给用户审批，接受则写入文件，拒绝则丢弃。

### 为什么需要

**业务需求**：Agent 全自主执行完毕后，用户批量审批所有改动。

**具体场景**：用户说"在第三章埋伏笔，第七章揭开"

```
Agent 自主执行：
  ① read_file("outline.md")         ← 读大纲
  ② read_file("chapters/03.md")     ← 读第三章
  ③ read_file("chapters/07.md")     ← 读第七章
  ④ edit_file("chapters/03.md"...)  ← 改第三章 → 存缓冲区，不落盘
  ⑤ edit_file("chapters/07.md"...)  ← 改第七章 → 存缓冲区，不落盘
  ⑥ Agent 执行结束
      │
      ▼ 汇总展示
  chapters/03.md: "旧段落" → "埋了伏笔的新段落"
  chapters/07.md: "旧段落" → "揭开伏笔的新段落"
      │
      ├── 用户点"接受" → flush()   → 写入文件
      └── 用户点"拒绝" → discard() → 丢弃，文件不变
```

**本质**：数据库事务搬到文件系统上。Agent 开始 = BEGIN，接受 = COMMIT，拒绝 = ROLLBACK。

### 为什么不用框架自带的 interrupt_on

```python
# 框架内置方式
agent = create_deep_agent(interrupt_on={"write_file": True, "edit_file": True})
```

| | 框架 interrupt_on | BufferedFilesystemBackend |
|---|---|---|
| 中断时机 | **每个**写操作暂停一次 | Agent **跑完后**统一 |
| 用户体验 | 改第三章暂停→审批→改第七章暂停→审批 | 一次看到所有改动，统一审批 |
| Agent 状态 | 中断后暂停等审批 | 全程不中断，自主跑完 |

### 实现方式

继承 FilesystemBackend，重写三个方法：

```python
class BufferedFilesystemBackend(FilesystemBackend):

    write()  → 不写文件，存缓冲区
    edit()   → 不改文件，存缓冲区
    read()   → 先查缓冲区，没有再读真实文件（关键！）
```

`read()` 必须查缓冲区的原因：Agent 可能先 `write_file("chapters/03.md", ...)` 创建新章节，然后马上 `read_file("chapters/03.md")` 检查自己写的内容。如果 read 不查缓冲区，Agent 会看到"文件不存在"。

外部接口：

```python
backend.get_changes()  → 返回所有待审批改动（给前端展示）
backend.flush()        → 审批通过，全部写入文件系统
backend.discard()      → 审批拒绝，丢弃缓冲区
```

### 实现细节

#### 1. 缓冲区数据结构：操作日志（事件列表）

```python
self.write_buffer = [
    {"type": "write", "path": "chapters/03.md", "content": "初始内容"},
    {"type": "edit",  "path": "chapters/03.md", "old": "旧文", "new": "新文", "replace_all": False},
]
```

不存"最终状态"，存"操作序列"。read 时按序重放，得到当前内容。

#### 2. read() 需要重放缓冲区

Agent 可能对同一个文件做多次操作：

```
write_file("chapters/03.md", "初始内容")     ← 缓冲记录 #1
edit_file("chapters/03.md", "旧文", "新文")   ← 缓冲记录 #2
read_file("chapters/03.md")                  ← 需要返回重放后的结果
```

read 的逻辑：

```python
def read(self, file_path, offset=0, limit=2000):
    # 1. 收集该文件在缓冲区里的所有操作
    ops = [op for op in self.write_buffer if op["path"] == file_path]

    if not ops:
        # 缓冲区无操作，透传到真实文件系统
        return super().read(file_path, offset, limit)

    # 2. 从磁盘原始内容开始（如果文件存在）
    #    如果第一个操作是 write，从空内容开始
    content = 磁盘原始内容 or ""

    # 3. 按序重放所有操作
    for op in ops:
        if op["type"] == "write":
            content = op["content"]
        elif op["type"] == "edit":
            content = content.replace(op["old"], op["new"])

    # 4. 按 offset/limit 分页返回
    return 分页后的 content
```

#### 3. edit() 在缓冲模式下的匹配

Agent 第二次 edit 同一个文件时，old_string 应匹配**重放后的内容**，不是磁盘原始内容：

```
write_file("chapters/03.md", "他走进了森林。")           ← 缓冲
edit_file("chapters/03.md", "森林", "黑暗森林")           ← 缓冲内容变为"他走进了黑暗森林。"
edit_file("chapters/03.md", "黑暗森林", "幽深的黑暗森林")  ← 应该能匹配到"黑暗森林"
```

所以 edit() 也需要先重放，验证 old_string 存在且唯一，再追加操作到缓冲区：

```python
def edit(self, file_path, old_string, new_string, replace_all=False):
    # 1. 重放得到当前内容
    current = self._replay(file_path)

    # 2. 验证 old_string 匹配情况
    count = current.count(old_string)
    if count == 0:
        return EditResult(error="old_string not found")
    if count > 1 and not replace_all:
        return EditResult(error=f"old_string appears {count} times")

    # 3. 验证通过，追加操作到缓冲区
    self.write_buffer.append({
        "type": "edit", "path": file_path,
        "old": old_string, "new": new_string,
        "replace_all": replace_all,
    })
    return EditResult(error=None, path=file_path, occurrences=count if replace_all else 1)
```

#### 4. _replay() 核心方法

read / edit / write 都依赖的内部方法，重放缓冲区得到文件当前内容：

```python
def _replay(self, file_path) -> str | None:
    """重放缓冲区，返回文件当前内容。None 表示文件不存在（磁盘+缓冲区都没有）"""
    ops = [op for op in self.write_buffer if op["path"] == file_path]

    if not ops:
        # 无缓冲操作，尝试读磁盘
        try:
            return 读磁盘原始内容
        except FileNotFoundError:
            return None

    # 有缓冲操作，确定起始内容
    if ops[0]["type"] == "write":
        content = ops[0]["content"]
        ops = ops[1:]
    else:
        content = 读磁盘原始内容  # edit 操作前提是文件已存在

    # 按序重放
    for op in ops:
        if op["type"] == "write":
            content = op["content"]
        elif op["type"] == "edit":
            if op["replace_all"]:
                content = content.replace(op["old"], op["new"])
            else:
                content = content.replace(op["old"], op["new"], 1)

    return content
```

#### 5. write() 对已存在文件的检查

框架原始行为：文件已存在时报错。缓冲模式下需要同时检查**磁盘和缓冲区**：

```python
def write(self, file_path, content):
    # 检查磁盘上是否已存在
    if 磁盘文件存在(file_path):
        return WriteResult(error=f"Cannot write to {file_path} because it already exists.")

    # 检查缓冲区是否已有 write 操作
    if any(op["path"] == file_path and op["type"] == "write" for op in self.write_buffer):
        return WriteResult(error=f"Cannot write to {file_path} because it already exists.")

    self.write_buffer.append({"type": "write", "path": file_path, "content": content})
    return WriteResult(error=None, path=file_path)
```

## 二-B、任务 2.1.3 — 启用 5 个特性，禁用 Shell

### 总览

| 特性 | 状态 | 对应中间件 | 写小说时干什么 |
|---|---|---|---|
| Planning | ✅ 启用 | TodoListMiddleware | 写作任务规划与进度追踪 |
| Filesystem | ✅ 启用 | FilesystemMiddleware | 读写章节文件、搜索全书内容（6 个工具） |
| Sub-agents | ✅ 启用 | SubAgentMiddleware | 委派子任务（一致性检查、逐章审阅等） |
| Smart defaults | ✅ 启用 | BASE_AGENT_PROMPT | 内置工具使用指南，白嫖 |
| Context mgmt | ✅ 启用 | SummarizationMiddleware | 长对话自动摘要，大输出存文件 |
| Shell | ❌ 禁用 | — | 写小说不需要跑命令，天然禁用 |

**关键**：这 5 个特性不是要"开启"的开关，而是框架默认中间件栈自带的。唯一要做的是选 `FilesystemBackend`（不选 `DockerSandboxBackend`），Shell 就自动没了。

### 1. Planning — 写作任务规划

框架给 Agent 两个工具：`write_todos` / `read_todos`

用户说"写第三章"时，Agent 会先给自己列清单：

```
Agent 的 todos：
☐ 读取大纲，确认第三章剧情方向
☐ 读取第二章结尾，确保续接
☐ 读取人物设定，确认出场角色
☐ 创建 chapters/03.md，写第三章初稿
```

逐个执行、逐个打勾。TodoListMiddleware 自动注入，零代码。

### 2. Filesystem — 6 个文件工具（核心）

| 工具 | 写小说时干什么 |
|---|---|
| `ls` | 看 chapters/ 下有几章了 |
| `read_file` | 读大纲、读前文、读人物设定 |
| `write_file` | 创建新章节 chapters/03.md |
| `edit_file` | 续写、改写、埋伏笔 |
| `glob` | `chapters/*.md` 找所有章节 |
| `grep` | 搜"李云飞"出现在哪些章节 |

FilesystemMiddleware 注入。我们用 BufferedFilesystemBackend 接管写操作。

### 3. Sub-agents — 子 Agent 委派

#### 框架行为（源码验证）

SubAgentMiddleware **始终自动注入**，无法关闭。即使 `create_deep_agent(subagents=None)`，框架也会自动创建一个内置 GP（General-Purpose）子 Agent。

主 Agent 通过 `task` 工具派子 Agent：

```python
# 主 Agent 的工具调用
task(description="逐章检查人物言行是否符合 characters.md 设定")
```

子 Agent 特性：
- **独立上下文窗口**：不挤占主 Agent 的 context，适合跨全书分析
- **共享同一 backend**：子 Agent 拿到的是同一个 `BufferedFilesystemBackend` 实例
- **独立 LLM 会话**：每次 `task()` 调用都是独立的 LLM 对话链（有 token 成本）
- **返回字符串报告**：子 Agent 运行完毕后，将结果以字符串形式返回给主 Agent

#### ⚠️ 关键约束：子 Agent 不应写文件

因为子 Agent 共享 `BufferedFilesystemBackend`，如果子 Agent 调用 `write_file` / `edit_file`，写操作也会进入缓冲区——但用户在审批时**无法区分**操作来自主 Agent 还是子 Agent。

**V1 决策**：通过 system_prompt 约束子 Agent 只做只读分析，不做写操作。

```
主 Agent system_prompt 中补充：
"使用 task 工具时，子 Agent 仅用于分析和检查，不得修改文件。所有文件修改由你（主 Agent）亲自执行。"
```

#### 五个业务场景

##### 场景 1：人物一致性检查（跨全书）

```
用户："检查李云飞的人物是否一致"

主 Agent → task("阅读 characters.md 中李云飞的设定，然后逐章检查：
                 1. 性格言行是否符合设定
                 2. 外貌描写是否矛盾
                 3. 称呼/关系是否前后一致
                 返回发现的矛盾列表")
         → 子 Agent 独立读 characters.md + 全部章节
         → 返回："{第3章: 李云飞说'我从不喝酒'，但第7章出现'他端起酒杯一饮而尽'}"
         → 主 Agent 汇总报告给用户 / 根据报告修复
```

**为什么需要子 Agent**：检查 20 章 × 5 个角色 = 100 次 read_file，主 Agent 的上下文窗口会被撑爆。子 Agent 的独立窗口解决这个问题。

##### 场景 2：伏笔/线索追踪

```
用户："帮我检查玉佩这条伏笔线是否完整"

主 Agent → task("grep '玉佩' 找到所有提及，按章节顺序列出：
                 1. 首次出现（铺设）
                 2. 中间提及（强化）
                 3. 最终揭示（收束）
                 评估伏笔线是否完整，是否有断裂")
         → 子 Agent: grep → 逐章 read_file 相关段落 → 分析伏笔链
         → 返回伏笔追踪报告
```

##### 场景 3：大纲对齐审查

```
用户："检查实际章节是否偏离了大纲"

主 Agent → task("阅读 outline.md 的章节规划，然后逐章对比：
                 1. 该章是否覆盖了大纲要求的情节点
                 2. 是否有大纲中没有但章节中出现的偏离
                 返回偏离清单")
         → 子 Agent: read outline.md → 逐章对比
         → 返回对齐报告
```

##### 场景 4：章节质量评审

```
用户："评审第 5-10 章的写作质量"

主 Agent → task("阅读 chapters/05.md 到 chapters/10.md，从以下维度评分（1-10）：
                 1. 节奏感  2. 对话自然度  3. 描写密度  4. 情节推进
                 每章给出具体改进建议")
         → 子 Agent 独立完成大量阅读 + 分析
         → 返回评审报告
```

##### 场景 5：全书统计分析

```
用户："分析一下全书的数据"

主 Agent → task("统计全书：
                 1. 各角色出场次数和章节分布
                 2. 各章节字数分布
                 3. 对话/描写/叙述的比例
                 4. 场景转换频率")
         → 子 Agent: glob + grep + read_file 遍历全书
         → 返回统计数据
```

#### 设计原则总结

| 原则 | 说明 |
|---|---|
| 子 Agent = **只读分析** | 跨全书的检查、统计、评审，不写文件 |
| 主 Agent = **执行修改** | 根据子 Agent 报告决定是否修改，亲自调 edit_file |
| 独立上下文 | 分析 20+ 章节不会撑爆主 Agent 窗口 |
| 成本意识 | 每次 task() 是独立 LLM 会话，大任务才用 |

#### V1 决策

- **不自定义 SubAgent**：框架内置 GP 子 Agent 已满足需求（通用工具集 + 自然语言指令）
- **不传 `subagents` 参数**：`create_deep_agent()` 无需指定，内置 GP 自动可用
- **system_prompt 约束只读**：防止子 Agent 写文件混入审批缓冲区
- **后续迭代**：如果 V1 发现子 Agent 质量不够，再考虑自定义专业化 SubAgent（如 ConsistencyCheckerAgent）

### 4. Smart defaults — 内置 Prompt

BASE_AGENT_PROMPT 教 Agent 怎么高效使用工具，举例：

- "修改文件前先 read_file，不要盲改"
- "write_file 只能创建新文件，改已有文件用 edit_file"
- "edit_file 的 old_string 必须精确匹配"
- "输出太大会自动存文件，去文件里看"

这就是为什么 system_prompt 只需要 25 行——工具怎么用，框架已经教了。

### 5. Context mgmt — 上下文管理

自动处理长对话和大输出，防止上下文爆炸：

| 机制 | 触发条件 | 行为 |
|---|---|---|
| 旧消息摘要 | 对话太长 | 早期消息压缩成摘要，保留最近的 |
| 大输出存文件 | 工具返回 > 20,000 token | 自动存到文件，Agent 拿到路径去读 |
| write_file 截断 | 旧的 write 内容 | 截断历史写入内容（原文已在文件里） |

写小说必须有这个：Agent 写一章 3000 字，对话十几轮，上下文很容易超限。SummarizationMiddleware 自动处理。

### 6. Shell — 天然禁用

`FilesystemBackend` 不实现 `SandboxBackendProtocol`，框架自动不创建 `execute` 工具。零配置。

## 二-C、任务 2.2 — 写缓冲 + 批量审批

### 2.2.1 与 2.1.2 的关系

2.2.1（Agent 执行期间 write_file/edit_file 不落盘，存缓冲区）和 2.1.2（BufferedFilesystemBackend）是**同一件事**。BufferedFilesystemBackend 本身就是 `create_deep_agent(backend=...)` 的参数，属于创建 Agent 的一部分。

已确定的结论（详见上方 2.1.2 节）：

| 决策点 | 结论 |
|---|---|
| 方案 | 继承 FilesystemBackend，重写 write() / edit() / read() |
| 缓冲区结构 | 操作日志（事件列表），不存最终状态 |
| write() | 不落盘，追加到缓冲区；同时检查磁盘+缓冲区防重复 |
| edit() | 不落盘，先 _replay() 验证 old_string 匹配，再追加到缓冲区 |
| read() | 先查缓冲区（_replay() 重放），没有才读磁盘 |
| _replay() | 核心内部方法，按序重放操作日志得到文件当前内容 |
| 外部接口 | get_changes() / flush() / discard() |
| 不用 interrupt_on | 框架逐次中断不符合批量审批需求 |

不再重复展开，实现细节见 2.1.2。

### 2.2.2 批量审批 — 卡片 + 编辑器 diff

#### 核心原则：边跑边推（实时流式）

**所有 Agent 操作都实时推送给前端**，不只是写操作。用户全程看到 Agent 在干什么：

```
Agent 操作                          前端实时显示
─────────────────                  ──────────────
read_file("outline.md")         →  📖 Read outline.md
read_file("chapters/03.md")     →  📖 Read chapters/03.md
grep("李云飞")                   →  🔍 Grep "李云飞"
write_todos([...])              →  📋 WriteTodo 3 steps
read_file("characters.md")     →  📖 Read characters.md
Agent 思考中...                  →  💭 Thinking 3s...（LLM token 流式输出）
edit_file("chapters/03.md"...) →  📄 chapters/03.md +10 -1  ✓ ×
Agent 思考中...                  →  💭 Thinking...
edit_file("chapters/07.md"...) →  📄 chapters/07.md +8 -1   ✓ ×
Agent 结束                      →  [Accept All] [Reject All]
```

框架原生支持：`agent.astream_events()` 推送每一个工具调用和 LLM 输出。我们把这些事件翻译成前端能渲染的格式即可。

技术实现两层：
- **所有操作的实时推送**：由 `astream_events()` 原生提供，每个工具调用、每段 LLM 输出都是一个事件
- **写操作的变更卡片**：由 BufferedFilesystemBackend 的 `on_change` 回调额外提供，携带 old/new diff 数据

#### UI 交互：对话卡片 + 编辑器 diff 视图

**对话面板（中间）**：紧凑卡片，只做入口

```
📄 chapters/03.md   +10 -1   ✓ ×
📄 chapters/07.md   +8  -1   ✓ ×

[Accept All]  [Reject All]     ← Agent 跑完后出现
```

**点击卡片 → 编辑器（右侧）切到 diff 视图**：红删绿增展示完整改动

```
┌──────────┬──────────────────┬──────────────────────────┐
│  左侧    │    中间 对话面板   │    右侧 编辑器            │
│  章节目录 │                  │                          │
│          │  Agent 回复...    │  ← 点卡片后切到 diff 视图  │
│          │                  │                          │
│          │  📄 03.md +10 -1 │  - 他望着远方，心中一片平静。│
│          │  📄 07.md +8 -1  │  + 他望着远方，指尖不自觉地  │
│          │                  │  + 摩挲着那枚玉佩...       │
│          │ [Accept All]     │                          │
│          │ [Reject All]     │     [Accept] [Reject]     │
└──────────┴──────────────────┴──────────────────────────┘
```

- 对话面板卡片：文件图标 + 文件名 + `+N -M` 统计 + ✓ × 快捷按钮
- 编辑器 diff 视图：红删绿增完整内容 + [接受] [拒绝] 按钮
- diff 数据来源：edit_file 的 old/new 参数天然就是 diff，不需要 diff 算法

#### 审批后的动作

| 操作 | 后端 | 前端 |
|---|---|---|
| 单个 Accept ✓ | 该操作从缓冲区取出，flush 到磁盘 | 编辑器刷新显示新内容 |
| 单个 Reject × | 该操作从缓冲区移除 | 编辑器保持原内容 |
| Accept All | backend.flush() | 编辑器刷新 |
| Reject All | backend.discard() | 什么都不变 |

## 三、任务 2.3 — RAG 语义搜索 tool（唯一自定义 tool）

### 为什么需要（grep vs 语义搜索）

Agent 已有 `grep`（字面匹配），但写小说经常需要概念级搜索：

| 场景 | grep | semantic_search |
|---|---|---|
| 搜"李云飞" | ✅ 精确命中 | ✅ |
| 搜"主角受伤的场景" | ❌ | ✅ 找到"鲜血从指缝间渗出" |
| 搜"师徒关系的描写" | ❌ | ✅ 找到师父教武功、临终托付 |
| 搜"前面提到过的那把剑" | ❌ | ✅ 找到"他拔出长剑"相关段落 |

grep 负责精确搜索，semantic_search 负责模糊/概念搜索，互补。

### 现成方案：LangChain `create_retriever_tool`

不用自己写搜索算法。LangChain 内置 `create_retriever_tool`，一行代码把 ChromaDB 检索器包装成 Agent 工具：

```python
from langchain_chroma import Chroma
from langchain.tools.retriever import create_retriever_tool
from sentence_transformers import SentenceTransformer

# 1. Embedding 模型
embedding = SentenceTransformer("BAAI/bge-small-zh-v1.5")  # 512 维，中文专精

# 2. ChromaDB 向量库（每部作品一个 collection）
vector_store = Chroma(
    collection_name=f"work_{work_id}",
    embedding_function=embedding,
    persist_directory="./chroma_db",
)

# 3. 转成检索器
retriever = vector_store.as_retriever(search_kwargs={"k": 5})

# 4. 一行包装成 Agent 工具
semantic_search = create_retriever_tool(
    retriever,
    name="semantic_search",
    description="对全书章节内容进行语义搜索，找到与查询最相关的段落。用于一致性检查、情节回溯、查找相关描写。",
)

# 5. 传给 DeepAgents
agent = create_deep_agent(
    tools=[semantic_search],  # 和内置 6 个文件工具并列
    ...
)
```

搜索精度、相似度计算、结果排序全部由 ChromaDB + LangChain 处理。

### 我们需要写的两件事

#### 1. 章节切块 + 灌入 ChromaDB

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(

    chunk_overlap=50,     # 10% 重叠，防止切断句子

chunks = splitter.split_text(chapter_content)

    texts=chunks,

```

切块参数来自 CRUD-RAG 中文 benchmark 研究推荐：500 字 / 50 字重叠，中文标点作为分隔优先级。

#### 2. 章节变更后更新索引

flush 写入磁盘后，触发向量索引更新：

```python

for op in self.write_buffer:
```

### 知识库功能迁移（从 pgvector → ChromaDB）

旧系统的 `VectorStoreService` 除了"章节语义搜索"外，还承担了**用户知识库**功能：

## 四、任务 2.4 — 章节文件系统 API

### 是什么

给**前端**用的 REST API，替换原有的数据库章节 CRUD。前端的左侧章节目录和右侧编辑器都需要这些 API 来读写章节文件。

**关键理解**：Agent 通过 `FilesystemBackend` 的 6 个内置工具操作文件，前端通过这些 REST API 操作**同一批文件**。文件系统是 Agent 和前端的共享数据层。

### 新旧方式对比

| 操作 | 旧方式（DB） | 新方式（文件系统） |
|---|---|---|
| 列出章节 | `SELECT * FROM chapters WHERE work_id=?` | `ls chapters/` + 解析每个文件的 frontmatter |
| 读取章节 | `chapter.content` 字段 | `read_file("chapters/01.md")` |
| 创建章节 | `INSERT INTO chapters` | `write_file("chapters/xx.md", frontmatter+内容)` |
| 更新章节 | `UPDATE chapters SET content=?` | 直接覆写文件内容（前端编辑器保存） |
| 删除章节 | `DELETE FROM chapters` | 删除文件 `chapters/xx.md` |
| 获取标题 | `chapter.title` 字段 | 解析 frontmatter 的 `title` 字段 |
| 获取字数 | `chapter.word_count` 字段 | 读取正文后实时计算 |

### 前端使用场景

```
左侧章节目录：
  GET /api/works/{work_id}/chapters       ← ls chapters/ + 解析 frontmatter
  → [{number: "01", title: "黎明", status: "draft", word_count: 2500}, ...]

右侧编辑器：
  GET /api/works/{work_id}/chapters/01    ← read_file("chapters/01.md")
  → {content: "月光穿过窗帘...", title: "黎明", status: "draft"}

  PUT /api/works/{work_id}/chapters/01    ← 覆写文件
  ← {content: "编辑后的内容..."}
```

### frontmatter 解析

每个章节文件开头包含 YAML frontmatter，API 需要解析它：

```markdown
---
title: 黎明
status: draft
---

月光穿过窗帘的缝隙，洒在地板上...
```

需要封装一个 frontmatter 解析工具：

```python
import yaml

def parse_chapter(content: str) -> dict:
    """解析章节文件，分离 frontmatter 和正文"""
    if content.startswith("---"):
        parts = content.split("---", 2)
        meta = yaml.safe_load(parts[1])
        body = parts[2].strip()
    else:
        meta = {}
        body = content
    return {
        "title": meta.get("title", ""),
        "status": meta.get("status", "draft"),
        "content": body,
        "word_count": len(body),
    }
```

### 与 Agent 的关系

```
                    ┌──────────────────┐
                    │   文件系统        │
                    │  chapters/01.md  │
                    │  chapters/02.md  │
                    │  outline.md      │
                    └───────┬──────────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
     Agent（写入时）    前端（读取时）   前端（编辑器保存时）
     BufferedBackend   GET API         PUT API
     → 缓冲 → 审批    → 直接读文件     → 直接写文件
       → flush 落盘
```

- Agent 的写操作经过 BufferedFilesystemBackend 缓冲 + 审批
- 前端的读写操作直接操作文件（用户在编辑器里手动编辑不需要审批）
- 两者操作同一批文件，文件系统是唯一数据源

### 需要实现的 API 端点

| 方法 | 路径 | 功能 |
|---|---|---|
| GET | `/api/works/{id}/chapters` | 列出所有章节（ls + frontmatter） |
| GET | `/api/works/{id}/chapters/{num}` | 读取单个章节 |
| POST | `/api/works/{id}/chapters` | 创建新章节 |
| PUT | `/api/works/{id}/chapters/{num}` | 更新章节内容 |
| DELETE | `/api/works/{id}/chapters/{num}` | 删除章节 |
| GET | `/api/works/{id}/files/{path}` | 读取任意文件（大纲、人物等） |
| PUT | `/api/works/{id}/files/{path}` | 更新任意文件 |

## 五、任务 2.5 — Agent API 端点

### 是什么

把现有的 Agent 对话 API（`POST /agent/chat/stream`）从自研 `WritingAgentGraph` 切换到 DeepAgents `create_deep_agent()`。API 端点的"壳"基本不变，里面的"引擎"换了。

### 现在 vs 重构后

```
现在：
  POST /agent/chat/stream
       → WritingAgentGraph（自研，几百行）
         ├── IntentClassifier
         ├── PlanGenerator
         ├── ToolExecutor
```

#### 2. 事件翻译：框架事件 → 前端 SSE 格式

`astream_events()` 推送框架原生事件，我们翻译成前端能渲染的格式：

|---|---|---|

| `on_tool_end(read_file)` | `{type: "tool_end", tool: "read_file"}` | ✓ |
| `on_tool_start(grep)` | `{type: "tool_start", tool: "grep", args: {...}}` | 🔍 Grep "李云飞" |

| 端点 | 功能 |

### BufferedFilesystemBackend 生命周期

每次用户发消息 → 创建 backend → Agent 跑完 → 等审批 → flush/discard → 销毁：

```python
# 全局内存字典，临时持有待审批的 backend
pending_backends: dict[str, BufferedFilesystemBackend] = {}

# 用户发消息时
backend = BufferedFilesystemBackend(root_dir=work_path)
agent = create_deep_agent(backend=backend, ...)
await agent.astream_events(...)

# Agent 跑完，暂存等审批
pending_backends[conversation_id] = backend

# 用户审批时
backend = pending_backends.pop(conversation_id)
backend.flush()   # 接受 → 写入磁盘
# 或
backend.discard()  # 拒绝 → 丢弃
```

### 会话层级调整：去掉 chapter_id

**现状**：`agent_sessions` 表有 `chapter_id` 字段，会话挂在章节下：

```
作品
  └── 章节 1
  │     ├── 会话 A
  │     └── 会话 B
  └── 章节 2
        └── 会话 C
```

**问题**：重构后 Agent 的 `root_dir` 设在 Work 级别，一次对话经常跨多个章节（"第三章埋伏笔，第七章揭开"），会话绑定到某个章节没有意义。

**调整**：会话只挂在 Work 下，去掉 `chapter_id`：

```
作品
  ├── 会话 A（可能涉及多个章节）
  ├── 会话 B
  └── 会话 C
```
