## 💎 核心策略：复用Planning组件

### 为什么复用很重要？

Planning模式虽然技术架构不如Chat，但包含6个月积累的**高质量组件**。复用这些组件可以：

- ✅ **节省10.5天开发时间**（约2周）
- ✅ **降低bug风险**（复用已验证代码）
- ✅ **保持一致性**（两种模式共享基础）
- ✅ **降低维护成本**（统一工具和错误处理）

### 13个可复用点分类

#### 类别1: 直接复用（6个，零改动）⭐⭐⭐⭐⭐
```
工具系统 → P0-02统一时直接复用
Checkpointer → P1-01实现chat_stream时共享
JSON解析器 → 需要时直接调用
重试机制 → 各处可用
Prompt模板库 → P1-05优化Prompt时复用
模型选择器 → P0-01修复task_type时复用
```

#### 类别2: 适配复用（4个，轻度修改）
```
进度回调机制 → P1-01实现chat_stream时适配
错误处理逻辑 → P2-02优化错误处理时提取
上下文构建 → P1-04上下文管理时提取
AgentState结构 → P1-01实现chat_stream时扩展
```

#### 类别3: 设计思想复用（3个，重新实现）
```
三阶段执行模式 → 借鉴思想优化Chat流程
智能并行执行 → 用LangGraph Send API实现
结果聚合策略 → P1阶段实现响应生成时借鉴
```

```
                │
                ↓
┌─────────────────────────────────────────────┐
│           LangGraph Agent                    │

│  └─ _build_final_response()                 │
└─────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────┐

│    └─ mode="planning" → chat_with_planning()│
└───────────────┬─────────────────────────────┘
                │
        ┌───────┴───────┐
        ↓               ↓
┌──────────────┐ ┌─────────────────────────┐
│ Chat模式     │ │ Planning模式            │

│              │ │                         │

└──────────────┘ └─────────────────────────┘
        │
        ↓
┌─────────────────────────────────────────────┐
│           LangGraph Graph                    │
│  ├─ intent_classifier                       │
│  ├─ writing_agent / planning_agent / ...    │
│  ├─ tools (统一后的工具系统)                │
│  └─ checkpointer                            │
└─────────────────────────────────────────────┘
```

### 关键决策点

#### 决策点1：P0完成后（第3周末）
**问题**：是否继续P1阶段？
**决策依据**：
- P0修复是否成功
- 代码质量是否达标
- 团队资源是否充足

**退出条件**：
- P0修复失败或耗时过长
- 发现更严重的架构问题

#### 决策点2：POC验证后（第4周末）
**问题**：chat_stream是否可行？
**验证指标**：
- astream()事件粒度是否足够
- 响应时间是否优于planning
- 代码复杂度是否可控

**退出条件**：
- POC验证失败
- 性能无法接受
- 技术方案过于复杂

#### 决策点3：P1完成后（第8周末）
**问题**：是否灰度发布？
**评估标准**：
- 功能完整性
- 稳定性指标
- 性能表现

**退出条件**：
- 关键功能缺失
- 稳定性不达标
- 用户体验不佳

### 应急预案

#### 方案A：快速降级
如果P1阶段出现问题，立即降级到P0修复后的Planning模式：
- 保留修复后的代码质量改进
- 使用稳定的Planning模式
- 调整优化策略

#### 方案B：分阶段实施

- 只做P0修复，维持现状

- 其他功能延后

#### 方案C：完全放弃
如果风险过高：
- 保持现有Planning模式
- 仅做必要的P0修复
- 寻求其他优化路径
