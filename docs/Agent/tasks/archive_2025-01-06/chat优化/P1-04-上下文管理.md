# P1-04-上下文管理：历史压缩与注入策略

## 📋 文档信息

- **优先级**：P1（核心功能）
- **预估工作量**：2天
- **依赖**：P1-01、P1-02、P1-03完成（具备流式执行与前端展示能力）
- **验收标准**：
  - 同一会话下，token窗口占用率维持在80%以内
  - 长对话（>30轮）仍能保持关键指令与设定
  - 支持最少两种上下文压缩策略（摘要+检索）
  - 提供可观测的上下文注入日志

---

## 🎯 功能概述

在React模式下重构上下文管理体系，确保长对话场景中模型能够获取稳定且精炼的历史信息。通过分层记忆、token预算与可观测性，实现「记得住、放得下、看得懂」的上下文管理能力，为后续Prompt优化与生产可用性打下基础。

### 核心目标

1. **分层记忆体系**：区分短期上下文、会话总结、长期记忆/知识库，按需注入
2. **动态压缩策略**：结合摘要与检索，控制token占用并保留关键信息
3. **上下文注入标准化**：统一在graph入口对上下文进行构建，保证事件流的一致性
4. **可观测性与调试**：记录上下文决策过程，便于调试与后续优化

---

## 🔍 技术分析

### 现状痛点

> Planning模式通过人工编排规避token溢出，但在React模式下我们需要LangGraph自动推进节点，旧方案无法复用。

- **历史消息直接堆叠**：当前聊天实现是简单拼接所有历史消息，长对话必然超过模型上下文窗口
- **缺少角色设定保留机制**：系统提示、用户偏好无法保证在长对话中持续存在
- **无上下文观测能力**：无法查看每次请求实际注入了哪些内容，定位问题困难
- **压缩策略缺位**：没有摘要或检索机制，导致关键信息被截断

### React模式中的约束

1. **事件驱动**：上下文必须在进入LangGraph之前准备好，并在节点执行过程中维持一致
2. **工具调用较多**：工具结果可能长篇幅，需要即时压缩
3. **多模型协作**：不同节点（意图识别、写作Agent、工具Agent）可能需要不同的上下文视图
4. **需要保持线程安全**：会话级上下文存储需避免并发写冲突

---

## 🏗️ 实现方案

### 1. 上下文内存模型设计

```
┌─────────────────────────────────────────────┐
│                 ContextStore                │
│  ┌─────────┬──────────┬──────────────────┐ │
│  │ Short   │ Summary  │ LongTerm / KB    │ │
│  │ Memory  │ Memory   │ (Vector Store)   │ │
│  └─────────┴──────────┴──────────────────┘ │
└─────────────────────────────────────────────┘
```

- **Short Memory**：最近N轮对话原文，着重保持最新语境（默认保存5-8轮）
- **Summary Memory**：基于对话节点自动生成的滚动摘要，提取用户目标、约束、偏好
- **LongTerm/KB**：对话中产生的重要事实或外部知识，写入向量库，按需检索

> 所有内存均挂载在会话级`thread_id`下，通过统一的`ContextManager`接口访问。

### 2. token预算与压缩策略

| 组件 | 预算占比 | 说明 |
|------|----------|------|
| 系统提示（Prompt模板） | 20% | 包含角色设定、行为准则 |
| 摘要上下文 | 25% | 压缩后的历史摘要，多次对话共享 |
| 近期对话原文 | 35% | 最近N轮，保障即时语境 |
| 工具结果精华 | 15% | 重要的外部信息 |
| 预留区 | 5% | 防止偶发超限 |

压缩动作需要在以下时机触发：

1. **新用户消息到达** → 更新Short Memory，检查token是否超限
2. **工具节点输出超长内容** → 通过LLM模板生成摘要，写入Summary/LongTerm
3. **对话轮次超过阈值** → 主动触发全量摘要更新，并清理过旧原文

### 3. LangGraph集成点

```python
async def chat_stream(...):
    context_bundle = await context_manager.build_context(session_id)

    input_state = AgentState(
        messages=context_bundle.messages,  # 系统提示 + 摘要 + 近期对话
        session_id=session_id,
        memory=context_bundle.metadata,
        ...
    )
```

- `ContextManager.build_context()`负责组装用于`AgentState`的消息列表与附加元数据
- 在`graph`的节点执行后，通过`ContextManager.update()`接收新事件（用户消息、工具结果、Agent输出），同步维护内存
- 对于摘要生成/向量检索，作为LangGraph中的独立工具节点调用，保证幂等性

### 4. 可观测性与调试

1. **上下文快照日志**：在每次构建上下文时记录`token_count`、`保留条目`、`丢弃条目`，写入`ContextEvent`
2. **前端调试面板**（P2阶段配合实现）：允许在开发模式查看上次请求的上下文组成
3. **Metrics指标**：
   - `context.token_usage`：三种内存的token占比
   - `context.summary_refresh_count`：摘要刷新次数
   - `context.vector_hits`：向量检索命中率

### 5. 错误与回退策略

- 摘要生成失败 → 回退到保留最近N轮原文，并记录告警
- 向量检索超时 → 使用缓存的上一次检索结果或空列表
- token预算仍超限 → 逐步裁剪最早的原文消息，必要时提示前端用户压缩对话

## 🗺️ 实施步骤

1. **搭建ContextManager骨架**
   - 定义`ContextStore`接口及默认实现（Redis/内存）
   - 支持`load/save/update`操作，保证幂等
2. **实现摘要与检索子系统**
   - 摘要模板：区分对话摘要与工具结果摘要
   - 向量库接入：可先使用现有Embedding服务
3. **整合LangGraph事件**
   - 在`chat_stream()`入口和事件回调中注入上下文构建/回写
   - 为关键节点添加上下文钩子（如写作Agent、工具Agent）
4. **加上指标与日志**
   - 统一输出`ContextEvent`，在后端日志与前端调试中展示
5. **验证与调优**
   - 构造长对话测试用例（60轮对话、混合工具调用）
   - 度量token使用情况，调整预算阈值与摘要策略

## 📌 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 摘要质量不稳定 | 关键信息丢失 | 引入回放机制，必要时保留原文备份 |
| 向量检索性能 | 响应时延增加 | 采用异步预写+缓存策略，必要时降级为摘要模式 |
| token预算配置不当 | 对话被强制截断 | 提供动态调试工具，允许 run-time 调整阈值 |
| 多线程更新冲突 | 上下文错乱 | 使用基于`session_id`的锁或CAS机制，确保一致性 |
