# Multi-Agent 架构设计

> 文档版本: 1.0
> 创建日期: 2025-12-06
> 状态: 设计方案

---

## 概述

本文档详细描述 Multi-Agent 写作系统的架构设计，基于 5 角色协作模式。

---

## 核心理念

### 为什么需要 Multi-Agent？

> "单 AI + 大窗口，治标不治本。需要架构层的解法。"

**三个核心词**: 分工、校验、外挂记忆

### 编辑部类比

想象一个编辑部：
- 有人写大纲
- 有人写初稿
- 有人专盯人设
- 有人检查剧情矛盾
- 总编拍板定稿

没有全能者，但组合起来能产出完整作品。

---

## 5 角色协作流程

```
┌─────────────┐
│   大纲师    │ 生成章节大纲（冲突/角色/情绪曲线）
└──────┬──────┘
       ↓ JSON
┌─────────────┐
│    主笔     │ 根据大纲写初稿，不做逻辑判断
└──────┬──────┘
       ↓ JSON
┌─────────────┐     ┌─────────────┐
│  角色守护   │     │  逻辑审计   │  并行校验
└──────┬──────┘     └──────┬──────┘
       └────────┬──────────┘
                ↓ 汇总
       ┌─────────────┐
       │    总编     │ 裁决冲突，输出定稿
       └─────────────┘
```

## 角色详细设计

### 角色1: 大纲师 (OutlineAgent)

#### 职责
生成章节大纲（冲突/角色/情绪曲线）

#### 输入
- 总纲
- 人设库
- 前文摘要

#### 输出格式

```json
{
  "chapter_id": 15,
  "title": "章节标题",
  "core_conflict": "本章核心冲突",
  "characters": ["角色A", "角色B"],
  "emotion_curve": {
    "start": "压抑",
    "mid": "爆发",
    "end": "留悬念"
  },
  "foreshadowing": "本章埋下的伏笔",
  "connection_to_previous": "承接上章的具体点"
}
```

#### System Prompt 要点

```
你是一个网文大纲策划师。你的唯一任务是根据总纲和人设库，为指定章节生成结构化大纲。

输出要求：
- 只输出JSON格式，不写任何正文
- 每章必须包含：核心冲突、出场角色、情绪曲线、本章伏笔、承接点

禁止事项：
- 不要写正文
- 不要发挥创意改动人设
- 不要跳过任何字段
```

---

### 角色2: 主笔 (WriterAgent)

#### 职责
根据大纲写初稿，严格执行，不自行发挥

#### 输入
- 大纲JSON
- 人设文档
- 前文内容（用于衔接）

#### 输出格式

```json
{
  "chapter_id": 15,
  "word_count": 1680,
  "content": "正文内容...",
  "dialogue_ratio": "45%",
  "pending_review": ["人设一致性", "逻辑连贯性"]
}
```

#### 风格锚定（硬性指标）

| 指标 | 要求 |
|------|------|
| 句子平均长度 | ≤ 20字 |
| 形容词使用率 | ≤ 5% |
| 感叹号 | 禁止 |
| 禁用词 | "竟然""居然""没想到" |
| 对话占比 | 40%-50% |

---

### 角色3: 角色守护 (CharacterGuard)

#### 职责
校验人设一致性（名字/性格/能力）

#### 检查清单

1. 角色名字是否正确（包括别称、昵称）
2. 角色性格是否符合设定
3. 角色口头禅是否正确使用/不误用
4. 角色能力边界是否被突破
5. 角色关系是否符合当前剧情进度

#### 输出格式

```json
{
  "chapter_id": 15,
  "status": "PASS | NEED_REVISION",
  "issues": [
    {
      "type": "性格偏离",
      "location": "第3段",
      "description": "问题描述",
      "suggestion": "修改建议"
    }
  ],
  "confidence": 0.85
}
```

#### 问题示例

```json
{
  "type": "性格偏离",
  "location": "第7段，苏晚的回应",
  "description": "苏晚说'我只是随便看看'——根据人设，苏晚性格是'外柔内刚，被质疑时会反击'，这里的反应过于软弱",
  "suggestion": "改为更有锋芒的回应，如'陆先生请我来，没说哪些房间不能进'"
}
```

---

### 角色4: 逻辑审计 (LogicAuditor)

#### 职责
检查剧情矛盾、时间线、因果漏洞

#### 检查清单

1. 时间线是否矛盾（与前文对照）
2. 空间逻辑是否合理（角色位置移动）
3. 因果关系是否成立
4. 前文伏笔是否被遗忘/矛盾
5. 角色已知信息是否被误用（角色不应知道的事）

#### 输出格式

```json
{
  "chapter_id": 15,
  "status": "PASS | NEED_REVISION",
  "issues": [
    {
      "type": "时间线矛盾",
      "location": "第1段",
      "description": "问题描述",
      "reference": "与第X章冲突",
      "suggestion": "修改建议"
    }
  ]
}
```

#### 问题示例

```json
{
  "type": "空间逻辑",
  "location": "第5段",
  "description": "老周说他在走廊拐角，但前文第12章明确写过'东侧走廊是直的，没有拐角'",
  "reference": "第12章第3段",
  "suggestion": "改为'老周站在走廊尽头的阴影里'"
}
```

---

### 角色5: 总编 (EditorAgent)

#### 职责
汇总校验结果，做最终裁决，输出定稿

#### 裁决优先级

```
逻辑自洽 > 人设一致 > 风格一致
```

#### 工作流程

1. 汇总所有issues
2. 判断是否有冲突（两个审核意见互相矛盾）
3. 如有冲突，按优先级裁决
4. 执行修改，输出定稿

#### 输出格式

```json
{
  "chapter_id": 15,
  "revision_summary": "修改摘要",
  "conflicts_resolved": [
    {
      "conflict": "冲突描述",
      "decision": "裁决结果",
      "reason": "理由"
    }
  ],
  "content": "最终定稿正文...",
  "word_count": 1720,
  "quality_score": 0.88
}
```

## 记忆系统设计

### 三件套架构

```
┌─────────────────────────────────────────────┐
│                记忆系统                      │
├─────────────┬─────────────┬─────────────────┤
│  向量数据库  │   摘要链    │  显性设定文档   │
│  (Chroma)   │ (每章摘要)  │   (人设圣经)    │
└─────────────┴─────────────┴─────────────────┘
```

### 1. 向量数据库

- 已完成章节切段、向量化存储
- Agent需要"回忆"时，语义检索最相关片段
- 比塞全文到上下文高效得多

### 2. 摘要链

每完成一章，自动生成结构化摘要：

```json
{
  "chapter_id": 15,
  "summary": "苏晚深夜探访书房，被管家老周撞见...",
  "character_updates": {
    "苏晚": "对陆沉的怀疑加深",
    "老周": "首次展现'知情者'姿态"
  },
  "plot_threads": {
    "new": ["书房密室线"],
    "advanced": ["苏晚调查线"],
    "dormant": ["陆沉前妻线"]
  },
  "foreshadowing": "老周的异常反应暗示他与陆沉的关系不简单"
}
```

### 3. 显性设定文档

一份不变的"圣经"，每个Agent工作前先读。包含：
- 世界观设定
- 角色完整人设
- 势力关系图
- 时间线大事记

## 冲突裁决机制

### 场景示例

> 角色守护说"苏晚反应要更强硬"
> 逻辑审计说"太强硬会暴露目的，违反'角色不应暴露已知信息'"

### 裁决流程

```
1. 识别冲突
2. 查看优先级：逻辑自洽 > 人设一致
3. 采取折中方案
4. 记录裁决理由
```

### 裁决结果

```json
{
  "conflict": "角色守护要求苏晚反应更强硬，但如果太强硬会暴露她的目的",
  "decision": "采取折中方案：苏晚的反应有锋芒但克制",
  "reason": "逻辑自洽优先级高于人设表现，但可以在不破坏逻辑的前提下增加性格色彩"
}
```

## 风格漂移防护

### 问题

> 写到第50章，文风从"冷峻克制"变成"中二热血"

### 解决方案

#### 1. 风格锚定Prompt

写死量化指标（见主笔部分）

#### 2. 周期性校验

每10章运行风格检测：

```json
{
  "check_range": "chapter_41_to_50",
  "metrics": {
    "avg_sentence_length": 18.3,
    "adjective_ratio": "4.2%",
    "exclamation_count": 0,
    "dialogue_ratio": "46%"
  },
  "status": "PASS",
  "drift_warning": "第47章对话占比降到38%，轻微偏离"
}
```
