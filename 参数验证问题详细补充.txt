=== 详细技术分析 ===

问题 1: users.py 的具体风险演练
URL: GET /api/v1/users?skip=0&limit=1000000&search=test
危害:
  - 数据库执行: SELECT * FROM users LIMIT 1000000 OFFSET 0
  - 内存占用: ~500MB (假设每条记录500字节)
  - 网络传输: ~500MB JSON响应
  - 服务器CPU: 100% 处理序列化
  - 其他请求: 全部超时

问题 2: admin.py 的性能影响分析
最坏情况: days=90
总查询数: 90天 × 2个COUNT查询 = 180次
每次查询耗时: ~10-50ms (取决于表大小)
总耗时: 1.8-9秒
数据库连接: 占用1条连接9秒

可改进方案: 使用CROSS JOIN自动填补日期
假设改进后耗时: 200-500ms (单一查询)
性能提升: 4-18倍

问题 3: chapters.reorder_chapters 的并发问题
场景: 用户A和用户B同时重新排序不同作品
问题: 如果允许超大列表(如10000条ID)
  - UPDATE chapters SET order = ... WHERE id IN (大量ID)
  - 数据库表级锁定
  - 其他用户的读写操作被阻塞
