核心发现（三大致命差异）
================================================================================

问题1：回调函数差异 【致命】

Planning模式回调（5个模式专用）：
  ✗ onPlan(plan) → 初始化任务列表
  ✗ onTaskStart(task) → 标记任务开始
  ✗ onTaskProgress(progress) → 更新任务进度
  ✗ onTaskDone(taskDone) → 标记任务完成，计算时间
  ✗ onStep(step) → 记录Agent步骤

React模式回调（2个模式专用）：
  ✗ onProgress(progress) → 更新当前进度事件
  ✗ onToolCall(toolCall) → 记录工具调用

结论：完全无法兼容，必须保持分离


问题2：UI组件无法共享 【致命】

TaskListPanel（Planning专用）
  - 显示task_id维度的任务列表
  - 显示进度条（completedCount/totalCount）
  - 显示执行时间

ProgressIndicator（React专用）
  - 显示step维度的进度事件
  - 显示intent_analysis/thinking/tool_execution步骤
  - 显示工具调用列表

结论：概念完全不同，无法互换


问题3：状态管理完全分离 【致命】

useAgentChat（Planning）：
  tasks: Task[]
  currentTaskId: number | null

useAgentChatStream（React）：
  currentProgress: ProgressEvent | null
  progressHistory: ProgressEvent[]
  toolCalls: ToolCallEvent[]

结论：两套独立的状态体系，无法合并


★ 总结：强行整合会导致代码复杂度激增，不推荐！

推荐方案（容器组件方案）
================================================================================

使用场景：

Page级别选择mode：
  // pages/WritingPage.tsx
  <AgentContainer mode="planning" workId="123" />
  
  // pages/ReactDemoPage.tsx
  <AgentContainer mode="react" workId="123" />


AgentContainer职责：
  ```typescript
  export default function AgentContainer({ mode = 'planning', ...props }) {
    if (mode === 'react') {
      return <AgentReactPanel {...props} />;
    }
    return <AgentChatPanel {...props} />;
  }
  ```


AgentReactPanel职责：
  - 使用useAgentChatStream hook
  - 显示ProgressIndicator（而非TaskListPanel）
  - 显示进度历史和工具调用
  - 完整的错误处理

================================================================================
为什么推荐这个方案？
================================================================================

✅ 优点：
  1. 改动最小化（仅新增2个文件）
  2. 不破坏现有代码（保持向后兼容）
  3. 风险极低（新增代码，非修改现有）
  4. 清晰分离（Planning和React完全独立）
  5. 易于维护（修改一个模式不影响另一个）
  6. 类型安全（各模式独立的类型系统）
  7. 易于扩展（新增模式只需新建Panel）
  8. Hook规则合规（没有条件式Hook）

❌ 为什么不用其他方案？

方案B（Hook整合）：
  ✗ 违反React Hook规则（条件式Hook）
  ✗ 返回类型Union复杂化
  ✗ 调用者需要处理type guard
  ✗ 代码可读性下降

方案C（API统一）：
  ✗ 需要后端改造
  ✗ 当前两个API已清晰分离
  ✗ 收益不大
  ✗ 成本高
